# 투자 실행 2단계: 저장과 공통 장부 연결

개발 브랜치: codex/investment-execution. 운영 DB·API·실제 자산 자료에 접근하거나 반영하지 않았다.

## 구현 범위

- 투자 과정의 생성·조회·일시 중단·재개·부분 종료와 종료 시점 보고서 저장.
- 포트폴리오당 진행/중단 과정 1개. 같은 시작 요청의 재전송은 기존 과정을 반환한다.
- 시작 안내를 확인한 뒤 잔고·계획으로부터 안내 내용이 달라졌으면 다시 검토해야 한다.
- 기존 원화 예수금과 달러 잔액을 먼저 사용한다. 아직 입금하지 않은 추가 투자금은 별도로 지정한다.
- ISA·IRP·연금 계좌는 원화 이체 출발 계좌에서 제외한다.
- 매수 목표 변경 시 작업 ID·체결·원가·원본 계획을 보존하고, 실제 잔고로 남은 이체·환전 안내를 재계산한다. 새 작업이 필요한 경우에만 새 ID를 추가한다.
- 변경 이유·요청·이전/새 목표를 이력으로 저장한다. 오래된 버전의 입력은 실제 장부와 연결을 함께 미반영한다.
- 기존 매매·NH 알림톡·달러 이벤트 입력에 선택적인 execution 연결 정보를 추가했다. 기존 요청에는 영향을 주지 않도록 null 연결 정보를 요청 비교에서 제거한다.
- 장부 저장과 투자 작업 연결은 같은 금융 트랜잭션을 사용한다. 기존 기록 연결·해제는 잔고·보유·원가를 변경하지 않는다.
- 원본 기록 취소·삭제를 조회에 반영한다. 취소된 요청을 다시 전송해도 거래를 다시 생성하지 않는다.
- 연결 후보는 작업에 맞는 최근 원본 최대 100개, 시작 후보 계획은 최근 25개만 조회한다. 전체 과거 거래를 탭마다 가져오는 새 경로를 추가하지 않았다.
- 실행에 사용한 계획의 기존 연결/해제를 다른 경로에서 변경하지 못하게 했다. 투자 실행의 공통 연결 경로로 관리한다. 진행 중 계획의 보관 처리도 제한한다.

## 저장 구조와 보안

기존 public 장부 20개 테이블과 보안 스냅샷을 유지한다. 별도의 비공개 portfolio_execution 스키마에 다음 5개 테이블을 추가한다.

| 테이블 | 역할 |
| --- | --- |
| cycles | 원본 계획, 시작 설정, 상태, 목표 버전, 종료 보고서 |
| steps | 안정적인 작업 ID, 목표, 선행 조건, 목표 변경 이력 |
| attempts | 실행 출처와 고유 식별자, 원본 근거, 반영 상태 |
| results | 확인된 사실, 수량·가격·통화, 장부 반영 상태 |
| record_links | 기존 실제 기록 참조와 연결 해제 이력 |

기존 rebalance_plan_links는 매매와 원본 계획 행의 관계를 유지하며, record_links는 결과와 그 원본 참조를 보관한다. 동일한 실제 거래를 다시 장부에 생성하지 않는다. 사용 중인 계획의 별도 연결 변경을 차단해 두 관계가 엇갈리지 않게 한다.

서버 초기화에서 반복 적용 가능한 추가 DDL과 보안을 같은 트랜잭션에 적용한다. 최초 스키마 생성에는 DB CREATE 권한이 필요하다. 이미 생성된 경우 스키마 소유자는 DB CREATE 권한 없이 반복 초기화할 수 있게 한다. 배포 전 실제 연결 역할의 생성 가능 여부를 확인하고, 부족하면 승인된 관리용 연결로 스키마를 미리 생성·소유권 설정해야 한다. 앱이 권한을 자동 확대하지 않는다. 새 스키마 소유자 확인, 5개 테이블 RLS 활성화, PUBLIC·anon·authenticated·service_role의 접근 권한 제거를 적용한다. 허용 정책이나 FORCE RLS를 추가하지 않는다. 정상 접근은 기존 소유자/BYPASSRLS 백엔드 연결을 사용한다. Data API를 켜거나 기존 public 권한 스냅샷·변경 버전을 덮어쓰지 않는다.

모든 신규 HTTP 경로는 기존 세션 인증 미들웨어를 사용한다. 프런트엔드에 DB 키나 접속 문자열을 추가하지 않았다.

## 후속 자동화 접점과 한계

execution_confirmations는 외부 통신이 없는 내부 모의 실행 접점이다. 주문 API, 주문 승인, 예약 작업, 상시 실행 프로그램은 구현하지 않았다. HTTP에서 모의 결과를 주입하거나 주문을 제출하는 경로도 없다.

모의 체결 근거를 먼저 저장하고 같은 기존 매매 저장소로 장부를 반영한다. 장부 반영이 실패하면 근거는 남으며 장부만 재시도한다. 체결 불명확 상태는 장부에 반영하지 않는다. 계획 변경 뒤 늦게 도착한 사실은 기존 버전으로 보존하며 최신 버전으로 반영하려면 명시적인 검토가 필요하다.

고유 원본 식별자가 같은 결과의 재조회, 동시 장부 저장, 부분 체결 결과, 식별 가능한 NH 주문번호 중복 도착을 양방향으로 검증했다. 알림톡이 먼저 장부에 반영된 경우 원본 기록을 재사용하고 모의 결과는 중복으로 표시하여 잔고·진행 수량을 다시 더하지 않는다. 실제 증권사 응답, 주문별/체결별 식별 규칙, 누적 체결 API의 역순 응답, 수수료·주문 정정·자동 승인은 미검증이다. 임의로 구성한 source_key만으로 실제 증권사의 중복을 해결했다고 간주하지 않는다. 미국 주문에는 아직 증권사 고유 체결 식별자를 사용한 자동 연동이 없다.

## 합성 검증 결과

- pytest: 358 통과, 5개 기존 외부 DB 의존 테스트 제외. 외부 네트워크와 운영 연결은 테스트에서 차단한다.
- verify_investment_execution.py: 매 실행마다 127.0.0.1:55438에 새 합성 DB를 만들고 종료 시 삭제. 생성/중복 요청, 실제 원화 이체, 부분 체결, 원가, 잘못된 연결의 전체 롤백, 중단/재개, 목표 증가/축소 재계산, 모의 체결 보존과 실패 복구, 늦게 도착한 결과, 식별 가능한 교차 출처 중복 차단, 기록 취소, 부분 종료 보고서, 신규 비공개 테이블 접근 차단, 비슈퍼유저 소유자/BYPASSRLS 역할의 반복 초기화·생성·매수·취소 통과.
- verify_bookkeeping_integrity.py: 기존 매매·환전 동시 요청, 입출금 취소, 과거 거래 원가 재계산, 음수 잔고 복구, 예금 입력·취소, 실제 PostgreSQL 실패 롤백 검증 7개 묶음 통과.
- verify_security.py: 기존 20개 public 테이블 보안·역할별 차단·정상 장부 기능·반복 초기화·권한 복구 검증 6개 묶음 통과.
- 보안 검증 스크립트에서 ACL 표시 순서가 아닌 실제 권한·위임 옵션을 비교하도록 테스트만 보완했다. 운영 권한 변경 로직은 바꾸지 않았다.
- 화면은 이번 단계에서 변경하지 않았다. 기존 로컬 합성 미리보기는 메모리 방식이며, 실제 DB 저장 화면으로 전환된 것이 아니다.

## 다음 단계와 운영 반영

다음은 계획서 3단계다. 4번 저장 계획에서 투자 시작, 5번·8번의 동일 입력 폼/초안/재시도 사용, 입력 후 진행 상황 갱신, 기존 기록 연결과 취소 안내를 실제 화면에 연결한다. 새 백엔드 제공 여부를 확인해 버전 차이가 있으면 새 투자 실행만 비활성화하고 기존 기록 입력을 유지한다.

승인 전 main 병합·push·배포는 하지 않는다. 최종 배포 시 최신 백업과 복구 확인 후 서버를 적용하고 신규 권한·정상 기능을 확인해야 한다. 코드 롤백은 비공개 추가 테이블을 유지한 채 이전 서버/화면으로 복귀한다. 투자 종료·코드 롤백은 실제 매매나 금융 기록을 취소하지 않는다. 금융 기록 취소는 기존 장부 기능으로 별도 처리한다.
