## 구현·검증된 것과 실제 운영 상태

기존 AWS 앱의 NH 클라이언트·토큰 캐시를 재사용하는 조회, 지급 이자/세금/원금 분리, 입출금·현금 흐름과 실제 장부 대조, 중복 방지·원자적 저장·취소, 일일 실행기와 화면은 로컬에 구현되어 있다. 구현된 전체 자동 경로가 현재 운영에서 실행된다는 뜻은 아니다.

핵심 코드:

- `data/cma_nh.py`, `logic/cma_statement.py`: 기존 NH 연결로 거래·입출금·잔고 수집 및 실제 지급 명세 해석.
- `logic/cma_interest.py`, `logic/cma_reconciliation.py`: 잔고 상태·장부 대조·순이자 증거·초기 차액 보류.
- `data/repositories/cma.py`, `data/cma_schema.py`: 원자적 저장·중복 방지·권한·격리 테이블.
- `backend/cma_interest.py`, `backend/routers/cma.py`, `logic/cma_policy.py`: 실행·API·쓰기 및 신뢰 형식 제한.
- `frontend/src/components/Tab4History/CmaIncomePanel.jsx`, `frontend/src/utils/cmaIncome.js`: 기존 5번 탭 내 CMA 패널.

실제 API 완료 응답은 `00166` + `조회가 완료되었습니다.`였다. 국내 종합거래 통화는 빈 문자열이며 입출금 명세에는 통화 필드가 없었다. 실제 CMA 상품 구분과 원금·세금·현금 연결/별도 입출금 대조로 검증하도록 보완했다. 새 NH 클라이언트·별도 토큰 발급 도구를 만들지 않는다.

마지막 검증: 백엔드 **562 통과·5 제외**, 프런트 전체 통과·격리 빌드 성공, 격리 PostgreSQL **18항목 통과 후 종료**. 실제 비식별 내역의 로컬 재생에서 현재 장부는 `INITIAL_BALANCE_REVIEW`, 초기 차액이 해소됐다고 가정한 합성 장부는 오늘 순이자 2,355원만 `MATCHED`였다. **초기 차액을 해소하는 실제 장부 절차는 아직 완성·실행하지 않았다.** 테스트 가정과 운영 완료를 혼동하지 않는다.

실제 NH 진단은 두 회차, 회차당 거래·입출금·잔고 각 1페이지로 업무 API 총 6회였다. 진단 전용 임시 릴리스를 사용했으며 종료 전에 운영을 다른 대화창의 **`fafd90c`로 복귀**, 임시 진단 설정 제거, 계좌 기록 불변을 확인했다. 전체 CMA 기능·스키마·스케줄러는 운영에 배포하지 않았다. 실제 장부 반영·매매·자동 활성화는 **0건**이다. 임시 SSH 인증자료는 삭제했다. 프런트도 다른 대화창의 배포 상태다.

## 남은 핵심 작업 — 이 순서로 완료

1. **초기 누적분 정리 경로를 완성한다.** 확인된 35,455원과 당일 2,355원을 분리하고, 초기 누적 수익임을 감사 기록에 남겨 장부 기준을 맞추는 최소 절차를 정한다. 필요하면 기존 NH 내역을 더 확인하되 사용자가 이미 제공한 정보를 다시 묻지 않는다. 날짜를 지어내지 않고 외부 입금으로 처리하지 않으며, 현재 초기 차액 차단을 단순 해제해 전체 차액을 당일 이자로 넣지 않는다.
2. **기존 일일 경로를 실제 명세에 연결해 끝낸다.** 명시적 권한 확보 후 검증된 NH 형식을 신뢰 목록에 등록하고, 초기 정리 후 실제 지급 순이자만 하루 한 번 반영되도록 완성한다. 중복 실행·실행 중 출금·세금·상품 전환·누락된 실행일의 처리에 필요한 시험을 기존 구조 안에서 수행한다. 기존 스케줄 설정으로 지급일 누락이 생기는지는 확인하고 필요한 범위만 보완한다.
3. **병합·배포·실제 검증으로 마무리한다.** 사용자 승인과 최신 배포 기준을 확인한 뒤 CMA 변경을 커밋/main 병합하고 AWS 및 필요한 화면을 배포한다. 기존 환전/미국 주식 개발을 보존하고 실제 순이자의 장부·이익 반영과 중복 방지를 확인한다. 다음 지급일의 자동 성공은 그날 명세 발생 후 확인할 수 있으므로 배포 시점에 이미 확인했다고 말하지 않는다. 실제 매매는 실행하지 않는다.

완료 기준: 기존 연결로 실제 지급 명세 조회 → 순이자 계산 → 장부 원자적 반영 → 포트폴리오 이익 반영 → 같은 지급 건 재실행에도 중복 없음 → 다음 지급일 자동 실행으로 이어짐. 초기 누적분의 중복/당일 오인도 없어야 한다.

## 승인 경계와 종료 시 대화

조회·확인은 사용자가 포괄 승인했다. 실제 매매는 계속 금지다. 사용자의 포괄 요청만으로 운영 권한이 모두 해결됐다고 가정하지 않는다. `logic/cma_policy.py`의 `NH_COMMON_CMA_PAID_V1` 신뢰 목록 등록은 자동 승인 심사가 미래 자동 장부 반영을 허용하는 지속적 변경으로 판단해 **거절했고 적용되지 않았다**. 현재 `VALIDATED_STATEMENT_PROFILES=frozenset()`이고 쓰기 플래그는 기본 0이다. 다른 경로/환경 설정으로 이 거절을 우회하지 않는다. 시험 프로세스의 합성 신뢰 주입은 운영 승인이나 운영 적용이 아니다.

마지막으로 사용자에게 **CMA 신뢰 형식 등록·초기 누적 이자 정리·이자 자동 장부 반영·main 병합·AWS/화면 배포**를 한 번에 묶은 승인을 물었다. 사용자는 이후 취침 때문에 중단을 요청했고, 그 범위의 명시적 승인을 답하지 않았다. 내일 단순한 재개 요청을 해당 운영 승인에 대한 응답으로 임의 간주하지 않는다. 필요한 로컬 완성 작업을 먼저 해 구체적으로 검토 가능하게 만들고, 실제 차단 작업/운영 적용 전에는 이 묶음의 명시적 승인만 확인한다. 이미 허용된 읽기·로컬 개발에 대해 반복 승인 요청을 만들지 않는다.

예상 추가 시간 1~2시간은 사용자에게 제시한 **예상치**이며 완료 보장이 아니다. 오늘은 더 진행하지 않기로 했고 자동 재개·알림·예약을 만들지 않았다.
