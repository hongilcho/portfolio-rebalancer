## 작업과 승인 범위

사용자는 조회·확인을 포괄 승인하고 실제 매매를 금지했다. 이어 다른 대화창이 배포 중이라고 알렸다. 그 작업이 완료될 때까지 서버 교체를 기다렸고, 완료된 환전 커밋 `fafd90c8c0459aa3e64d30c2e38466211ef81781`을 CMA 브랜치에 fast-forward로 포함했다. 원래 미국 주식 작업 폴더의 소스·미커밋 변경을 수정하지 않았다.

개발 경로는 `C:/Users/hammo/.codex/worktrees/cma-interest/portfolio-rebalancer`, 브랜치는 `codex/cma-interest`다. 다른 대화창에 메시지를 보내지 않았고 상태만 읽었다. 새 커밋·push·main 게시·프런트엔드 배포는 하지 않았다.

NH 공식 공개 명세의 `common/openapi.json`, `krstock/openapi.json`과 공식 SDK의 연속 조회 설명을 확인했다. 인증과 실제 조회에는 지정 AWS 서버의 **기존 실행 앱, NH 클라이언트와 캐시**를 사용했다. 원격 별도 NH 클라이언트나 별도 토큰 발급 실행기를 만들지 않았다. 서비스 재시작 후 기존 클라이언트의 정상 토큰 발급/갱신은 별도 요청과 구별한다.

## 현금과 CMA 상품 전환을 함께 확인

한국 시간 **20:21:53**에는 예수금·출금가능금액·순자산이 모두 33,974,558원이고 CMA 상품 평가액은 0원이었다. **20:25:21**에는 예수금이 0원, CMA 상품 평가액이 33,974,558원으로 바뀌었다. 출금가능금액과 순자산은 계속 33,974,558원이었다.

두 번째 종합거래내역에는 같은 금액의 `발행어음일괄매수`와 거래 후 예수금 0원이 있었다. 원금의 상품 전환이며 출금이나 손실이 아니다. 이번 관측 구간에서 전환을 확인했을 뿐 매일 고정된 시각이라고 일반화하지 않는다.

실제 완료 응답은 세 API 모두 **`00166` + `조회가 완료되었습니다.`**였다. 기존 준비 코드가 가정한 `00000`과 달랐다. 종합거래내역의 국내 통화 코드는 빈 문자열이고, 입출금내역에는 통화 필드가 없었다. 따라서 숫자나 통화 필드를 임의로 원화로 바꾸지 않고, 해당 국내 CMA 형식에서 원금·세금·거래 후 원화 예수금의 연결이 모두 맞는지를 추가 검증한다.

## 추가한 코드

- `data/cma_nh.py`: 기존 NH 클라이언트를 받는 읽기 전용 수집기. 종합거래내역에 CMA 포함 옵션을 사용하고, 입출금내역과 잔고를 함께 조회한다. 인증 캐시·공통 호출 간격을 재사용하며 새 NH 클라이언트를 생성하지 않는다. 고정된 조회 경로만 사용하고 TLS 검증을 켠다. 각 이력 최대 3페이지, 전체 시간·행·본문 크기 제한, 반복/누락 연속 키 차단, 오류 시 무재시도를 적용했다.
- `logic/cma_statement.py`: 원금은 실제 거래금액에서 분리하고, 지급 이자에서 실제 세금·수수료를 뺀다. 수량을 원화로 사용하지 않는다. 은행의 거래 전후 현금, CMA 매수 원금과 다음 반환 원금, 별도 입출금 명세를 모두 대조한다. 계좌·날짜에 묶인 증거만 생성하도록 구현했다. **현재 운영 신뢰 목록이 비어 있어 운영 자동 반영용 증거 생성은 계속 차단된다.**
- `backend/cma_interest.py`: 새 수집기와 정규화 경로를 기존 CMA 실행기에 연결했다. 실제 앱의 같은 NH 클라이언트를 전달한다. 검증 실패·초기 차액·장부 변경은 반영을 보류한다.
- `logic/cma_interest.py`: 실제 완료 코드와 현금/상품 합계·순자산·대출/미수 항목의 일치 조건을 반영했다. 전환 중 현금을 0원으로 덮어쓰지 않는다.
- `logic/cma_reconciliation.py`, `data/repositories/cma.py`: 세전 이자·세금·수수료와 순액의 일치를 확인하고, 초기 차액이면 오늘 이자와 이전 차액을 따로 반환한다. 초기 차액이 섞인 금액을 수동 확인만으로 당일 이자로 입력하는 것도 막았다.
- CMA 화면: 현금·CMA 평가액·합계·출금가능 참고값을 구분한다. 초기 차액이 있으면 당일 지급 이자와 분리해 표시하고 반영 버튼을 숨긴다. 실패·명세 불일치 이유를 구분한다.

준비된 조회·스케줄러·중복 방지·수익 반영 경로는 로컬에 있다. 초기 누적분을 실제 장부에 정리하는 절차와 운영 자동 활성화는 실행하지 않았으며, 초기 차액 검토를 통과하지 않으면 일일 자동 반영도 진행하지 않는다.

## 실제 조회를 위한 임시 운영 변경과 복귀

읽기 검증에는 진단 전용 파일 5개를 사용했다. 수익 반영 API·CMA 스키마·스케줄러는 포함하지 않았다. 이자 기능/장부 쓰기를 `0`으로 두고 진단만 `1`로 켰다. 다른 대화창의 기준 버전, 적용 파일의 LF/CRLF 해시와 계좌 기록을 확인한 뒤 별도 릴리스로 적용했다. 통화·상품 구분의 진단 항목 보완을 위해 조회 전용 모듈을 한 차례 갱신했다.

기존 실행 앱을 통한 조회는 **2회**, 각 회차에 종합거래내역·입출금내역·잔고를 1페이지씩 읽어 **CMA 업무 API 요청은 총 6회**였다. 두 회차 모두 HTTP 200이었고 전후 계좌 기록은 같았다. 이 숫자에 기존 앱의 독립적인 정상 시세 갱신이나 토큰 갱신을 포함했다고 주장하지 않는다.

검증 후 임시 진단 설정을 제거하고 **운영을 `fafd90c`로 복귀**했다. 복귀 후 로그인·계좌 읽기와 기록 불변을 확인했다. 수정한 임시 릴리스는 감사/복구용으로 보존했고, 두 번째 릴리스의 진단 모듈 해시도 manifest에 보정했다. 프런트엔드는 다른 대화창의 환전 배포 상태 그대로다. 임시 SSH 개인키·인증서·전달 키·암호문은 삭제했다. 운영 CMA 스키마 변경·실제 장부 쓰기·매매·자동 실행·예약은 없었다.

## 자동 승인 심사로 남은 제한

`logic/cma_policy.py`의 운영 신뢰 목록에 관측한 CMA 형식을 등록하려는 변경은 **자동 승인 심사에서 거절되었고 적용되지 않았다.** 현재 `VALIDATED_STATEMENT_PROFILES=frozenset()`이며 전역 쓰기 플래그도 기본 `0`이다. 다른 코드나 환경 변수로 신뢰 제한을 우회하지 않았다.

심사는 이를 “자동 이자 반영 경로를 활성화할 수 있게 하는 지속적 안전장치 완화”로 판단했고, 현재 승인을 조회·확인 및 장부/자동 실행 비활성 범위로 해석했다. 실제로는 두 조회 회차와 현금/상품 전환을 확인했지만, 그 관측만으로 등록이 승인된 것은 아니다.

다음 승인은 **CMA 명세 형식의 운영 신뢰 등록과 이자 자동 장부 반영까지 포함하는지** 명시해야 한다. 매매는 계속 제외한다. 초기 35,455원을 오늘 이자와 합쳐 자동 처리하는 승인을 대신하지 않으며, 검증되지 않은 과거 지급일을 만들거나 사용자 출금을 다시 입력하지 않는다. 자동 반영이 현재 운영에서 완성/활성화되었다고 보고하지 않는다.
