## 운영 자료 읽기 전용 선행 검증

운영 서버의 별도 프로세스에서 기존 코드와 조회 통합 후보를 각각 5회 교차 실행했다.
같은 캐시 시세·배당을 사용하고, 공개 응답 전체를 비교했다. 아래는 중앙값이다.
운영 코드 파일·서비스·환경설정은 바꾸지 않았다.

| 조회 범위 | 기존 | 통합 후보 | 감소 | SQL 실행 횟수 |
|---|---:|---:|---:|---:|
| 미래 성장포트 | 1,315ms | 611ms | 53.5% | 7 → 2 |
| 일반투자 | 1,284ms | 577ms | 55.1% | 7 → 2 |
| 전체 금융자산 | 1,323ms | 617ms | 53.3% | 7 → 2 |
| 전체 자산·가상자산 포함 | 1,467ms | 618ms | 57.9% | 8 → 2 |
| 가상자산 단독 | 711ms | 570ms | 19.7% | 3 → 2 |

모든 비교 응답이 일치했고, 보호 대상 금융·감사 테이블 28개와 서비스 제어 설정은
변경되지 않았다. 금융 데이터 쓰기와 증권사 호출은 모두 0회였다.
상세 결과는 Git 제외 파일 `backups/batched-loading/production-readonly-preflight.json`에 있다.

이 수치는 그래프 서버 처리 구간의 시험 결과이며, 배포된 앱이나 브라우저 전체 로딩
시간의 측정값은 아니다. 인터넷 왕복, 최초 시세 수집, 브라우저 렌더링 시간은 별도다.

## 변경 1 — 그래프 자료의 DB 왕복 통합

`data/repositories/holding_history_batch.py`에서 금융·가상자산 평가 기록, 미확정 정정,
필요한 기존 거래·배당 캐시·원가 기준 기록을 한 번의 SELECT로 읽는다.
별도의 READ ONLY / REPEATABLE READ 설정 1회를 포함해 SQL 실행은 총 2회다.
조회 연결은 계산 전에 반환한다.

확정된 보유자산 지표만 있는 경우 과거 거래·배당 복원 자료는 읽지 않는다.
복원이 필요한 경우 그래프 시작일보다 앞선 거래도 보존한다. 기존 배당 캐시는
한 SELECT 안에서 가져오고 기존 Python 적격성 함수로 필요한 키를 선별한다.
새 시세 수집·배당 캐시 갱신·평가 기록 저장은 하지 않는다.
기존 `logic.holding_history.history` 계산기를 그대로 사용한다.

## 변경 2 — 반복하는 CMA 스키마 확인 제거

앱 시작 시 선택적 CMA 테이블 2개의 존재 여부만 확인하고 프로세스 안에 보관한다.
정상 시작 후 현황 요청의 SQL 실행은 2회에서 1회로 줄어든다.
예수금·수량·원가·이자·수수료 값은 캐시하지 않고 매번 DB에서 읽는다.
테이블이 일부만 있으면 기존처럼 오류로 드러내며, 실패를 준비 완료로 저장하지 않는다.
독립 호출에서 시작 상태가 없으면 기존 방식으로 안전하게 확인한다.
CMA 기능의 스키마 구성이 바뀌는 배포에서는 백엔드를 재시작해야 한다.
기존 시작 시 스키마 초기화 및 보안 적용 순서는 유지한다.

## 변경 3 — 보이는 자료부터 병렬 조회

전체 자산 종합 요약과 가상화폐 화면에서는 요약·그래프를 동시에 요청한다.
화면에 그래프가 나타날 때 기존 공통 조회 저장소의 요청·결과를 재사용한다.
가상자산 포함·제외는 독립된 키를 유지한다.

기간 성과의 상세 자료는 5번 매매 및 입출금 기록, 7번 분석 및 확인,
8번 투자 실행의 장부 입력창에서 필요할 때 요청한다.
다른 화면의 첫 조회에서 이 상세 요청을 대기하지 않는다.
장부 등록·수정·삭제 후 재조회와 무효화 경로는 유지한다.

  취소된 정정, 빈 배당 캐시, 알 수 없는 범위 등을 검증.
- CMA 기능 존재·부재 각각 조회 결과 일치와 SQL 2 → 1을 검증.
- 자료별 테이블 지문이 조회 전후 동일함을 검증.
- 프런트엔드에서 병렬 시작·중복 방지·독립 오류·포함 토글·장부 변경 경합·화면 복귀 검증.

재현: `python scripts/verify_batched_loading.py --reset`.
이 스크립트는 전용 루프백 PostgreSQL(55474)과 합성 DB만 허용하며 외부 통신을 차단한다.

실행 전 별도 합성 클러스터를 준비해야 하며 사용자 DB 설정을 읽지 않는다.
결과는 Git 제외 경로 `backups/batched-loading/postgres-result.json`에 기록한다.
