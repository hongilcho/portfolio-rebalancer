## 사용 흐름

1. **5번 매매 및 입출금 기록**에서 실제 매도 체결을 입력한다. ‘전량’은 같은 계좌·종목의 다른 매도 대기 행을 제외한 보유 수량을 채운다. 주문을 전송하는 버튼이 아니다.
2. 수수료·실제 차감 세금은 접힌 입력란에서 선택적으로 확인한다. 확인 체크 후 금액을 입력하면 예수금에도 함께 반영된다. 단가에 이미 포함한 비용을 다시 입력하지 않는다. 확인하지 않아도 매매는 저장할 수 있다.
3. 기록 조회의 매도 상세에 비용 전 손익·순손익을 표시한다.
4. **7번 분석 및 확인**의 ‘실현손익 · 매도 완료 이력’에서 계좌·종목·매도일별로 조회한다. ‘전량 매도 완료’, ‘전체 보유기간’으로 전환할 수 있다. 보유기간은 전체 이력 기준이며 날짜 필터는 매도별 손익에 적용된다.
5. 전량 매도 시 현재 투자자산 목록에서 제외된다. 종목 마스터·목표비중·리밸런싱 포함 설정·과거 거래는 유지한다. 재매수하면 새로운 보유기간으로 분리된다.
6. 잘못된 매도는 기존 기록 취소 흐름을 사용한다. 수량·원가·예수금·비용·달러 원가 상태를 복구하고 보고서는 남은 장부에서 다시 계산한다. 기존의 후속 거래 의존성·정정·최신 달러 이벤트 취소 규칙은 유지한다.

1번 현황에는 누적 매도손익의 작은 요약을 추가했다. 기존 보유자산 수익률과 기간 성과 그래프의 계산식·분모는 바꾸지 않는다. 매도이익은 이미 매도대금에 포함되므로 총자산에 재합산하지 않는다.

## 계산 및 데이터의 확실성

- 원가는 **계좌·종목별 이동평균**이다. 부분 매도에는 남은 원가와 확인된 매입 비용을 비례 배분한다.
- 비용 전 매도손익 = 매도대금 − 배분 취득원가.
- 순손익 = 비용 전 매도손익 − 배분 매입 비용 − 매도 비용. 취득원가·매입비용·매도비용을 모두 확인한 거래만 확정 순손익으로 집계한다.
- 요약의 ‘계산 가능한’ 손익과 ‘비용 확인 완료분’은 각각 확인 가능한 거래의 소계다. 미확인 거래 건수를 함께 표시한다. 전부 미확인인 소계는 0원으로 확정하지 않는다.
- 기존 수수료 없는 기록을 0원으로 소급 확정하지 않는다. 과거 기록은 비용 전 손익을 우선 확인하며, 기존 거래의 비용만 별도로 수정하는 기능은 이번 범위에 포함하지 않았다.
- 과거 매입 이력이 없을 수 있어 새 매도 시 매도 직전의 장부 원가도 저장한다. 전체 매매 이력으로 재계산할 수 있으면 이력을 우선하며, 부족할 때만 이 장부 기준을 사용하고 이전 매입 비용 미확인을 표시한다. 현재 장부 원가를 과거 매도로 잘못 적용하지 않도록 과거 날짜 삽입에는 현재 원가 스냅샷을 붙이지 않는다.
- 최초 등록·원가 정정 INIT는 매매수익이나 현금 입금으로 계산하지 않는다. 원가 정정이 포함된 보유기간을 구분한다.
- 미국 자산은 달러 가격 손익, 매도 기준환율로 원화 환산한 손익, 환율 효과를 분리한다. `원화 비용 전 손익 = 달러 가격 손익 × 매도 기준환율 + 환율 효과`. 매도 이후 보유 달러의 환차손익과 세금 신고 계산은 별개다.
- 배당은 저장된 공시 캐시와 기존 배당 계산기를 사용한 계산값이다. 추가 외부 조회를 하지 않으며 실제 입금 확인값으로 표현하지 않는다. 전량 매도 후 지급되는 배당도 배당락일의 보유 이력으로 귀속한다. 미국 배당은 달러로 표시한다.
- 기존 수동 배당금 총액은 그대로 보존하지만, 보유기간별 배분 근거가 없어 여러 기간에 복제하지 않는다. 캐시·기간 배분 근거가 없으면 확인 필요로 표시한다.

## 구성 및 성능

- `logic/realized_gains.py`: 외부 IO 없는 이력 재계산.
- `data/repositories/realized.py`: 포트폴리오 범위의 읽기 전용 repeatable-read 조회, 기존 캐시 배당 연결.
- `data/repositories/trade_costs.py`: 기존 매매 트랜잭션 안에서 비용·스냅샷 저장. 달러 원가 이벤트도 같은 트랜잭션에 포함.
- `GET /api/trades/realized`: 날짜·계좌·종목 필터. 날짜를 걸어도 매수 원가는 전체 이력에서 계산한다.
- 대시보드는 기존 배치 조회의 이력을 재사용하므로 추가 DB·시세 요청이 없다. 기록 조회는 현재 페이지에 매도가 있는 경우 보고서를 한 번 조회하며 행마다 조회하지 않는다.
- `trade_costs_protocol: 1`로 비용 지원 여부를 알린다. 새 프런트엔드는 비용을 보낼 때 구버전 백엔드에서 조용히 무시되지 않도록 먼저 확인한다.
- 이전 요청에 없던 null 비용 필드는 멱등 요청 비교에서 제외하여 업데이트 전 미완료 요청도 같은 요청으로 확인할 수 있다.

## 승인 후 반영 및 되돌리기

아직 운영 반영하지 않았다. 승인 후 최신 main/CMA 변경과 병합 검토하고 테스트한 뒤 다음 순서로 진행한다.

1. 운영 DB 백업 및 이전 정상 버전 식별.
2. 백엔드 배포. 기존 시작 시 스키마 초기화가 같은 잠금·트랜잭션 안에서 다음 두 nullable 열을 추가한다. 기존 행은 NULL이며 소급 계산값을 쓰지 않는다.

```sql
ALTER TABLE trade_history ADD COLUMN IF NOT EXISTS trade_costs JSONB;
ALTER TABLE trade_history ADD COLUMN IF NOT EXISTS accounting_basis JSONB;
```

3. 백엔드 capabilities와 읽기 조회·로그인 정상 동작 확인 후 프런트 배포. 실제 운영 매매 입력은 사용자 확인으로 수행한다.
4. 기존 자산 평가액·예수금·보유 수량 불변, 미확인 비용 표시, 실제 매도 시 기록/현황/분석 갱신 확인.

프런트만 먼저 되돌리는 것은 기존 API와 호환된다. 새 비용을 반영한 거래가 생긴 뒤 백엔드를 구버전으로 되돌리면 특히 달러 비용 취소의 이벤트 의미가 달라질 수 있으므로 무조건적인 구버전 장부 쓰기 재개는 피한다. 이 경우 쓰기를 잠시 중지하고 비용 취소 처리를 유지한 수정 버전으로 복구한다. 두 새 열은 그대로 남겨 이력을 보존한다. 열 삭제나 운영 자료 복원은 별도 검토 없이 실행하지 않는다.
