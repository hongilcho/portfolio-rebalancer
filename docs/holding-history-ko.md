# 보유자산 손익 추이와 전체 자산 통합 그래프

개발 기준: main `92464d6`. 작업 브랜치 `codex/holdings-profit-history`.
기존 기간 성과·금융 장부의 정의와 기록은 유지한다. 이 문서는 로컬 개발 결과이며 운영 적용 완료 보고서가 아니다.

## 사용자 화면

- 7번 분석 및 확인: 현황 카드와 같은 기준의 보유자산 손익 추이를 기본으로 표시한다. 기존 기간 성과는 ‘기준일 이후 운용 성과’를 펼쳐 본다.
- 전체 자산 종합 요약: 통합 손익·수익률·평가액 추이를 추가한다. 기존 가상자산 포함/제외 선택이 카드와 그래프에 함께 적용된다. 구성별 선은 선택해서 표시한다.
- 손익·수익률·평가액, 30일/90일/전체 범위, 일별/월말/연말 관측값을 선택한다. 월말/연말은 해당 시점의 보유자산 지표이며 월·연 기간 수익률이 아니다.
- 모바일에서는 SVG를 실제 화면 너비에 맞추고 화면을 가로로 스크롤하지 않는다. 그래프를 누르거나 이전/다음 버튼으로 날짜별 값을 확인한다. 키보드 방향키/Home/End도 지원한다. 상세 설명과 표는 접어 둔다.
- 마지막 ‘현재’ 점은 이미 불러온 현황 카드의 KPI를 직접 사용한다. 빈 점과 점선으로 확정 종가와 구분한다. 현재 값은 과거 기록으로 저장하지 않는다.

## 지표와 보존 계약

보유자산 손익은 기존 KPI `total_stock_profit`, 수익률은 `total_stock_return`이다. 기존 순수 평가손익과 배당 계산 엔진을 그대로 재사용한다. 현금은 총평가액에만 포함하며 수익률 분모는 보유자산 매입원가다. 개별 수익률은 원래 KPI의 소수 정밀도를 유지한다. 합산 수익률은 각 포트폴리오의 손익과 원가, 가상자산의 손익과 원가를 각각 더해 계산하며 수익률을 평균내지 않는다.

현재 보유자산 지표와 기간 성과는 의미가 다르다. 실현손익, CMA 현금 이자, 현금 자체의 환차손익, 거래비용을 기존 현황 KPI에 없는 방식으로 새로 더하지 않는다. 기존 지표 정의를 이번 작업에서 바꾸지 않는다. 매도 후 보유 구성이 바뀌면 보유자산 손익도 달라질 수 있으며 실현손익 이력은 기존 별도 화면에 남는다. 보유 원가가 0이면 수익률을 만들지 않는다.

원래 기간 손익은 종료 NAV − 시작 NAV − 순입금이고, 수익률은 날짜별 입출금을 고려한 기존 계산을 유지한다. 원래 기준일·NAV·입출금·종가 작업의 의미를 변경하지 않는다. 통합 기간 수익률은 이번 변경에 추가하지 않는다. 향후 추가한다면 포트폴리오 간 내부 이체 상계와 가상자산 입출금 이력이 별도로 필요하다.

## 일별 수집과 저장

- 기존 종가 작업이 당시 장부·시세·환율을 확정할 때 같은 평가 엔진으로 `payload.holding_metrics`를 함께 저장한다. NAV 수집은 유지하고 부가 지표의 근거가 부족하면 그 지표만 UNAVAILABLE로 남긴다. 당시 매매 이력·배당 캐시도 입력 장부에 동결하므로 미래의 배당/거래가 과거 기록에 섞이지 않는다. 배당 캐시가 없음을 배당 0으로 확정하지 않는다. 새 배당 수집기나 증권사 호출은 만들지 않는다.
- 가상자산 전용 기록은 `portfolio_analytics.crypto_snapshots`다. 날짜가 PK이며 전체 가상자산을 1번만 저장한다. 동시에 실행해도 `ON CONFLICT DO NOTHING`으로 첫 관측을 유지한다.
- 기존 백엔드 종가 스케줄러에 가상자산 관측을 연결한다. KRX 기록일의 예정 시각부터 10분 이내에, 기존 시세 캐시가 예정 시각 이후 갱신되었고 정상일 때만 저장한다. 조회 지연은 관측 시각에 반영한다. 1분 간격으로 상태를 재확인하며 과거 날짜나 10분 구간 이후 시세로 결손을 채우지 않는다. 휴장일 수집은 이번 범위에 없다. 공급자의 거래 틱 시각을 확정한 ‘가상자산 종가’가 아니라 해당 구간에 수집한 시세 관측이다. 출처·시세 캐시 시각·실제 관측 시각을 함께 보관한다.
- 가상자산 수집 실패가 금융자산 종가 작업을 중단하지 않는다. 지연 마감 다음 정규 마감일도 정상 처리한다. 외부 시세 연결은 운영 반영 이후에만 발생하며, 로컬 검증에서는 차단했다.
- 과거 조회 API는 새 기록에서는 지표 JSON만 읽어 매번 전체 동결 장부를 전송하지 않는다. 원본 보유내역·계좌번호·매매 원문·배당 캐시는 응답에 포함하지 않는다.

## 과거 기록과 정정

기존 10월 5일 이후 원본 스냅샷을 변경하지 않는다. 당시 동결된 수량·원가·가격을 읽고, 당시 날짜로 제한한 매매·배당 자료가 충분할 때만 조회 응답에서 RECONSTRUCTED로 재계산한다. 당시 배당 근거가 없거나 동결 수량과 매매 이력이 맞지 않으면 손익·수익률은 미확인이다. 이미 저장된 총평가액은 손익 근거가 부족해도 보존한다. 현재 수량·원가로 과거를 채우거나 현황 손익을 일정 금액만큼 옮기는 방식은 사용하지 않는다.

모든 구성 자산에 같은 날짜의 지표가 있어야 통합 손익을 표시한다. 누락 날짜는 0으로 처리하지 않고 선을 끊는다. 가상자산 과거 일별 보유 장부를 아직 저장하지 않았으므로, 과거 금융자산 기록만으로 10월 5일부터의 전체 통합선이 완성된다고 보장하지 않는다. 실제 복원 가능한 일자는 별도 승인된 운영 읽기 점검에서 확인해야 한다.

기존 감사 정정에서 과거 보유 수량을 수정하면 해당 스냅샷의 오래된 부가 지표를 무효화하여 다시 근거를 확인한다. 현금만 정정하면 보유자산 손익은 유지하고 평가액만 조정한다. 확인되지 않은 과거 정정은 해당 날짜 손익·수익률을 미확인으로 표시한다. 정정 취소는 기존 원본 payload 복원 경로를 사용한다.

## 접근 및 검증

새 private 스키마/테이블은 앱 DB 소유자만 관리한다. 초기화 시 소유권을 확인하고 RLS를 활성화하며 PUBLIC·anon·authenticated·service_role의 스키마/테이블 접근을 차단한다. 기존 public 테이블 목록이나 RLS 정책을 넓히지 않는다. 새 HTTP 경로 `/api/performance/holding-history`는 기존 로그인 보호를 받는 읽기 전용 경로다. 세션 전체를 읽기 전용으로 바꾸지 않고 단일 REPEATABLE READ READ ONLY 트랜잭션을 사용하여 풀에 반환한 연결의 후속 쓰기를 막지 않는다.

- 단위/회귀: `tests/test_holding_history.py`, 기존 종가·장부 정정·기간 성과 테스트.
- 프런트엔드: `frontend/tests/holdingHistory.test.js`, 전체 테스트·lint·프로덕션 빌드. 전체 요약 3개 화면의 의도된 마크업 기대값만 검토 후 갱신했다.
- 실제 PostgreSQL: `HISTORY_QA_PG_BIN`으로 설치된 PostgreSQL bin을 지정하고 `python -X utf8 scripts/verify_holding_history_postgres.py`. 루프백 임시 DB만 허용하고 종료 후 서버를 중지한다. 반복 초기화, 동시 중복 저장, 무변경 조회, 실제 연결 풀의 후속 쓰기, BYPASSRLS 역할을 포함한 공개 역할 차단, 롤백 등 6개 검증 결과는 `holding-history-postgres-evidence.json`에 기록한다.
- 검토 화면: `python scripts/review_holding_history.py`로 합성 자료 생성 후 Vite에서 `/dev/holding-history/index.html`. 실제 공통 집계 함수와 UI 컴포넌트를 사용하지만 실제 운영 데이터는 포함하지 않는다. 가상자산 기록 1일 누락도 의도적으로 포함하여 미합산·선 끊김을 검토한다.

## 승인 이후의 반영 절차

로컬 최종 검증: 백엔드 653개 통과·기존 제외 5개, 프런트엔드 223개 통과, 격리 PostgreSQL 6개 통과, lint·프로덕션 빌드 통과. 브라우저에서 모바일 뷰포트의 가로 넘침 없음, 그래프 포인터 선택, 날짜 이동, 가상자산 포함/제외 시 카드·그래프 동시 변경, 구성별 선을 확인했다. 실제 휴대폰 기기 검증과 운영 자료의 과거 복원 범위 확인은 수행하지 않았다. 합성 예시의 ‘모바일 폭으로 보기’ 버튼으로 사용자가 다시 확인할 수 있다.

이번 작업에서는 커밋·push·main 병합·배포·운영 DB 연결을 하지 않는다. 반영 승인 시 최신 main과 병렬 작업을 확인하고 검증한 뒤 앱 관련 모든 스키마 백업 및 금융 테이블 지문을 확보한다. 기존 백업 도구의 스키마 목록에 `portfolio_analytics`를 포함해야 한다. 초기화 권한과 소유권을 확인한 후 프런트엔드와 백엔드를 함께 배포한다. 금융 원본과 기존 기간 성과의 보존, 로그인·조회, 종가/가상자산 스케줄 상태를 확인한다. 실제 주문이나 시험 잔고를 운영에 만들지 않는다.

문제 시 이전 릴리스로 코드만 되돌린다. 추가 private 테이블과 새 payload 키를 삭제하지 않으며 기존 기간 성과와 원본 기록을 유지한다. 운영 백업 복원은 일반 코드 롤백과 구분하며 별도로 승인받는다.

## 2026-10-27 운영 반영 승인과 사전 점검

로컬 화면 검토 후 사용자가 커밋·main 병합·origin push·AWS 배포 및 보존 검증을 승인했다. 기존 AWS와 origin/main은 `92464d6`다. 배포 직전 관련 백엔드 회귀 71개, 프런트엔드 전체 223개, lint·빌드를 재확인했다. 최종 전체 백엔드 653개·기존 제외 5개와 격리 PostgreSQL 6개 검증 결과는 유지된다.

기존 앱 스키마의 custom-format 논리 백업(새 analytics 스키마도 포함하도록 필터 지정)과 서버 내 별도 JSONL 백업을 확보했다. archive 목록·해시를 확인했으나 운영 백업을 실제 복원하지는 않았다. 금융·감사 테이블 27개 및 기존 기간 성과 평가 기록 30개의 원본·조회 계산 결과 지문을 비교한다. 수수료 정책, 기존 RLS/권한, 시퀀스, 환경변수, 종가 설정은 보존한다. 새 private 스키마 접근 제한은 별도로 확인한다. 배포 검증에서는 실제 주문·장부 입력·과거 성과 수정·가상자산 과거 기록 생성을 하지 않는다.

검토용 `synthetic.json`은 생성 스크립트로 재현하는 합성 산출물이므로 Git에서 제외한다. 로컬 검토 화면 파일은 유지되며 `python scripts/review_holding_history.py`로 다시 만들 수 있다.
