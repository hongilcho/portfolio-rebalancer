# 로딩 개선 — 2026-10-04

## 변경 내용

- 주식·환율(5분), 가상자산(1분), 배당(24시간) 캐시가 만료되면 마지막 스냅샷을 먼저 반환하고 백그라운드에서 갱신합니다.
- 캐시 자체가 없으면 최초 수집을 기다립니다. TTL을 늘리거나 숫자를 임의로 채우지 않습니다.
- 프로세스 내 동시 갱신은 한 번만 수행합니다. 캐시 부재·강제 새로고침 요청도 이미 실행 중인 수집을 공유합니다.
- 수집 실패 시 기존 스냅샷을 보존하고 일반 조회의 재시도 간격을 30초로 제한합니다. 강제 새로고침은 재시도할 수 있습니다.
- BTC/ETH 중 하나가 누락된 수집 결과, 등록된 시세 수집 대상 종목의 0원 결과, 환율 제공자 실패로 나온 기본값을 새 정상 스냅샷으로 저장하지 않습니다.
- 배당 없음(`[]`)을 정상 DB 캐시로 취급합니다. 동일 요청에서 같은 종목의 강제 배당 수집을 반복하지 않습니다.
- 시세와 해당 시세의 환율을 하나의 요청 스냅샷으로 유지합니다. 갱신 중에도 원화 평가액 계산에 다른 시점의 환율이 섞이지 않도록 합니다.
- 전체·개별·가상자산 화면에 조회 기준 시각, 갱신 중, 갱신 실패를 표시합니다. 브라우저에 저장했던 상태도 현재 나이를 기준으로 오래된 데이터임을 표시합니다.
- 화면은 갱신 중일 때만 2초→5초 간격으로 재조회하며 최대 15회로 제한합니다. 완료·실패·화면 이동 시 중지합니다.
- 포트폴리오 변경 또는 수동 새로고침 후 이전 응답이 화면을 덮지 않도록 요청 순서를 확인합니다.
- 가상자산 화면의 최초 진입 강제 수집을 제거했습니다. 명시적 새로고침과 리밸런싱은 수집을 기다립니다.
- 강제 수집 실패는 HTTP 503으로 안내합니다. 이전 시세로 새 리밸런싱 계획을 조용히 생성하지 않습니다.
- GET 요청의 불필요한 JSON Content-Type 헤더를 제거해 CORS 사전 요청을 줄였습니다. JSON 쓰기 요청의 헤더는 유지합니다.
- 국내 배치 시세를 기다리는 동안 미국·금현물·예금 작업을 먼저 실행하고 결과의 입력 순서는 유지합니다.
- 환율 DB 캐시의 중복 저장을 제거했습니다.

## 검증

운영에서는 변경 전 일반 GET 요청만 측정했습니다. 계좌·잔고·거래를 변경하지 않았습니다.
운영 코드 변경·배포·push는 이번 검증에 포함하지 않았습니다.

| 변경 전 운영 API | 첫 요청 | 다음 요청 |
|---|---:|---:|
| 개별 bundle | 0.770초 | 0.532초 |
| 가상자산 포함 전체 요약 | 1.486초 | 0.636초 |

이때 주식 캐시는 유효했고 가상자산 캐시만 만료되어 있었습니다. 브라우저 전체 로딩 시간이나 최대 지연을 측정한 결과가 아닙니다.

외부 수집을 3초로 모의한 실제 localhost FastAPI + 별도 PostgreSQL 검증:

- 만료된 캐시가 있는 일반 bundle: 0.029초, `refreshing=true`.
- 같은 수집의 강제 새로고침: 3.000초 대기 후 `stale=false`.
- 브라우저에서 초기 전체 평가액 2,392,000원을 먼저 표시하고 백그라운드 갱신 후 2,493,000원으로 자동 변경됨.
- 모의 수집 실패 시 이전 평가액과 실패 안내가 유지됨.
- 합성 브라우저 시나리오: `scripts/local_ui_preview.py --simulate-refresh --port 8548`.
- 합성 상태 재현 경로 `/qa/reset-cache`는 위 로컬 검증 스크립트에서만 등록되며 실제 백엔드에는 없습니다.

회귀 테스트는 `tests/test_refreshing_cache.py`, `frontend/tests/marketStatus.test.js`에 추가했습니다.
운영 설정 파일 읽기, 실제 DB 연결, 외부 시세 네트워크 호출은 pytest에서 차단됩니다.

최종 검증: Python 81개 통과·기존 DB 의존 테스트 5개 제외, 프런트엔드 7개 통과, lint·build 성공.
합성 브라우저의 정상 갱신 시나리오에서 콘솔 경고·오류가 없었습니다. 의도한 강제 수집 실패는 503과 오류 배너로 확인했습니다.
스크린샷은 Git에서 제외되는 `backups/local_validation/loading_stale.png`, `loading_updated.png`, `loading_failed.png`에 보관했습니다.

## 한계와 배포

- 이미 확보한 캐시가 있어야 외부 수집 대기를 제거할 수 있습니다. 처음 등록한 종목의 배당 등 캐시가 없는 경우와 강제 새로고침은 여전히 외부 API 시간의 영향을 받습니다.
- 계좌·보유량·거래는 계속 DB에서 조회합니다. 따라서 운영 네트워크 왕복과 DB 조회 시간은 남습니다. 합성 결과를 운영 0.03초 보장으로 해석하면 안 됩니다.
- 브라우저 재조회가 끝나거나 탭을 닫으면 화면은 마지막 값에 머뭅니다. 표시 시각을 확인하고 필요하면 새로고침합니다.
- 갱신 중복 방지는 단일 백엔드 프로세스 기준입니다. 여러 워커·인스턴스를 운영한다면 분산 잠금 또는 수집 전용 작업을 별도로 검토합니다.
- DB 스키마 변경은 없습니다. API 필드 추가는 기존 프런트엔드와 호환됩니다.
- 사용자 지정 배포 방식: 개선 사항을 main에 한 번에 push하여 Vercel 자동 배포를 진행하고, Render는 같은 커밋으로 수동 재배포합니다. 새 상태 필드는 선택적으로 표시되므로 기존 백엔드 응답도 프런트엔드에서 처리할 수 있습니다. 로딩 개선은 Render 재배포 후 적용됩니다.
- 배포 후 캐시 만료 상태와 유효 상태의 응답시간·서버 처리시간을 다시 측정합니다.

## 첫 개별 조회의 배당 캐시 복원 개선 — 추가 작업

운영 반영 후 첫 bundle은 4.159초(서버 3.750초), 바로 다음 bundle은
0.578초(서버 0.406초)로 차이가 있었습니다. 첫 요청에서 보유 종목의
배당 DB 캐시를 8회 순차 조회하는 구조가 남아 있었습니다.

- `get_overview_batch_data()`의 기존 SQL에 보유 종목의 배당 캐시와 나이를
  포함했습니다. 계좌·보유량·거래와 같은 한 번의 DB 왕복에서 받으므로
  추가 배당 SELECT가 없습니다. 개별 bundle·단독 summary·전체 요약에 적용합니다.
- 서버 시작 시 저장된 배당 캐시를 메모리에 복원합니다. 시세 수집과
  별도 스레드로 실행하므로 외부 시세 수집 지연에 종속되지 않습니다.
- 복원은 아직 로드하지 않은 캐시에만 적용합니다. 늦게 도착한 DB 결과가
  최신 메모리 결과나 실행 중인 갱신을 덮지 않습니다.
- 실제 빈 배당 이력은 정상 캐시로 유지하며, DB에 없는 이력은 확인된
  배당 0원으로 바꾸지 않습니다. 기존 캐시 만료·강제 갱신 동작을 유지합니다.
- 스키마와 수익률 계산식, 프런트엔드는 변경하지 않습니다.

운영 Supabase에 **읽기 전용 연결**로 변경 전 방식과 변경 후 방식을
번갈아 3회 비교했습니다. 외부 수집과 DB 쓰기는 차단했습니다.

| 로컬 Python → 운영 Supabase | 변경 전 | 변경 후 |
|---|---:|---:|
| 첫 bundle 처리 | 0.241~0.292초 | 0.047~0.053초 |
| 추가 종목별 배당 SELECT | 8회 | 0회 |

동일한 보유 데이터·시세·배당 이력에서 개별 화면의 계산 결과가 정확히
같음을 확인했습니다. 전체 요약도 추가 배당 SELECT 0회를 확인했습니다.
측정 결과는 `backups/local_validation/first_load_optimized_profile.json`에
보관합니다. 로컬에서 측정한 값이며 Render의 개선 시간 보장은 아닙니다.

`tests/test_dividend_cache_batch.py`는 첫 조회·중복 종목·동시 복원,
빈 이력·누락 이력·만료 캐시·최신 결과 보존·강제 갱신·독립적인 시작 시
복원을 검증합니다. 배포 후 첫 요청 성능은 Render에서 다시 측정해야 합니다.

## 거래 내역·리밸런싱 반복 조회 제거 (2026-10-04)

- 거래 내역의 매도 종목 목록은 `/api/holdings/all?portfolio_id=...`로
  보유 잔고를 한 번에 가져옵니다. 계좌가 8개이면 HTTP 요청은 8회에서
  1회로 줄어듭니다. 종목 선택에 필요한 원본 수량·이름만 이용하므로
  계좌별 거래 이력 조회와 배당 계산을 거치지 않습니다.
- 잔고 결과는 현재 계좌 목록으로 제한하고 조회마다 교체합니다.
  포트폴리오 변경 후 늦게 도착한 이전 응답은 버립니다.
- 리밸런싱 입력은 대상 포트폴리오의 자산·계좌·보유량을
  `get_rebalance_batch_data()`의 한 SQL 문으로 조회합니다.
  자산의 기본값 처리는 기존 단독 조회와 공유합니다.
- 주문 수량을 계산하기 전 시세 강제 갱신과 실패 시 주문 계산 중단은
  유지합니다. 매매·이체·수익률 계산식과 DB 스키마는 변경하지 않습니다.

검증은 외부 네트워크가 차단된 테스트와 운영 백업을 복원한 별도 로컬
PostgreSQL 17.6의 **읽기 전용 연결**로 진행했습니다.

| 로컬 복원 데이터의 리밸런싱 입력 조회 | 변경 전 | 변경 후 |
|---|---:|---:|
| 계좌 8개인 포트폴리오 | 10회 | 1회 |
| 계좌 1개인 포트폴리오 | 3회 | 1회 |

두 포트폴리오의 NEW_CASH·DRIFT·PERIODIC 결과 총 6개가 변경 전과
정확히 일치했습니다. 원본 보유 잔고, 포트폴리오 범위와 빈 결과도
확인했습니다. 위 수치는 입력 DB 조회만 센 것이며 시세 갱신 내부의
조회는 포함하지 않습니다. 운영 응답시간 개선 폭은 배포 후 측정해야 합니다.

합성 데이터의 변경 전 결과 6개는 `3345988` 코드에서 생성한
`tests/fixtures/rebalance_before_batch.json`에 저장했습니다.
`tests/test_rebalance_batch.py`는 매매 수량·이체·예금·IRP·USD·비활성
보유종목·비중 제외·실현손익의 결과 보존을 확인합니다.
`tests/test_bulk_holdings.py`와 `frontend/tests/accountHoldings.test.js`는
조회 횟수, 포트폴리오 범위와 원본 잔고를 검증합니다.

백엔드 102개 통과·기존 DB 의존 테스트 5개 제외, 프런트엔드 17개 통과,
lint·build 성공. 이 변경을 push하면 Vercel은 자동 배포되며,
백엔드 개선 적용에는 Render에서 같은 커밋의 수동 배포가 필요합니다.

## 평가액·배당 계산 분리 (2026-10-04)

개별 대시보드와 전체 요약의 데이터 조회·캐시 준비는 API 라우터에서
처리하고, 요청 내 배당 계산 준비와 순수 집계는 다음 모듈로 분리했습니다.

| 모듈 | 역할 |
|---|---|
| `backend/valuation_service.py` | 계좌·종목마다 배당을 한 번 계산해 두 요약에서 공유. 포트폴리오별 입력 격리 |
| `logic/dividend_calculator.py` | 공급자가 전달한 배당 이력으로 세금·거래 시점 보유량·원본 매입단가 계산 |
| `logic/holding_valuation.py` | 개별 보유 종목의 평가액·배당·환차손익 계산 |
| `logic/portfolio_valuation.py` | 계좌·종목·통화별 요약과 KPI 계산. 보유량·거래·USD 시세 색인 |
| `logic/overview_valuation.py` | 포트폴리오 간 동일 티커 합산, 가중 평단가, 현금·가상자산 포함 총자산 집계 |

`logic/dividend_fetcher.py`의 기존 함수 호출 방식은 유지합니다.
이 함수는 캐시에서 배당 이력을 가져온 뒤 순수 배당 계산기로 넘깁니다.
네 개의 순수 계산 모듈은 DB·설정·시세 공급자 모듈을 가져오지 않으며,
전달된 입력을 변경하지 않습니다. 가격·환율·배당 캐시 정책과 DB 조회
횟수·스키마도 유지합니다.

- 동일 보유 종목을 계좌 요약과 종목 요약에서 각각 계산하던 배당 처리를
  요청 내 한 번으로 줄였습니다. 계좌별 과세 유형과 수동 배당 보정은
  서로 분리하고, 다음 요청에서는 다시 계산합니다.
- 전체 요약은 보유량·거래·USD 시세 색인을 한 번 만들어 각 포트폴리오에
  공유합니다. 한 포트폴리오의 계산 실패가 다른 포트폴리오를 막지 않는
  기존 동작도 유지합니다.
- 대시보드 라우터는 692줄에서 139줄, 포트폴리오 라우터는 461줄에서
  123줄로 줄었습니다. 계산은 보유 종목·종목 합산·표시 행·통화 KPI
  등의 역할별 함수에 배치했습니다.

변경 전 `dea1258`에서 합성 데이터로 생성한 전체 응답 지문 18개와
변경 후 응답이 모두 일치합니다. 정상·수동 배당 보정·0원 시세·시세
누락·빈 포트폴리오·환율 0의 조건에서 bundle과 가상자산 포함/제외
overview를 비교했습니다. 기존 테스트는 원본 평단가, 배당 시점의
