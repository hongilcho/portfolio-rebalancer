# CMA 읽기 전용 확인과 격리 PostgreSQL 검증

2026-10-14 사용자 승인에 따른 후속 결과. 기존 NH 연결을 통한 CMA 잔고 읽기 전용 확인과 격리 로컬 PostgreSQL 시험만 승인되었다. 실제 장부 반영·운영 활성화·배포는 승인되지 않았고 실행하지 않았다.

## 1. 기존 연결 확인: 앱 로그인에서 중단

현재 AWS 운영 주소는 `docs/aws-migration-ko.md`에 기록된 `https://portfolio-rebalancer-api.duckdns.org`다. 이전 대화 요약의 잘못된 주소로 시도한 첫 연결은 DNS 단계에서 실패했으며 NH 호출은 없었다. 이관 문서와 AWS Lightsail `GetInstance` 읽기로 실제 주소와 서버의 실행 상태를 확인했다.

기존 앱 비밀번호를 메모리에서만 사용하여 `/api/auth/verify`를 한 번 호출했지만 HTTP **401**로 거절되었다. 운영 앱이 로컬의 기존 비밀번호를 받아들이지 않는다는 사실까지만 확인했다. 비밀번호를 추측하거나 재시도하지 않았다. 앱 세션·계좌 목록·CMA 잔고는 아직 받지 못했고 **NH 조회 0회, 별도 NH 토큰 요청 0회**다. 인증값과 계좌번호를 결과 파일이나 콘솔에 기록하지 않았다.

앱의 기존 `/api/sync/namuh/compare`는 읽기 전용이며 CMA 계좌에서 현재 앱 프로세스의 `nh_api_client.fetch_account_balance()`를 호출한다. 이 경로를 사용할 준비를 했다. 새 NH 클라이언트/별도 토큰 발급으로 우회하지 않는다. 기존 클라이언트가 정상 조회 과정에서 만료된 토큰을 갱신할 가능성은 있으므로, 향후 이 경로의 성공 자체를 ‘토큰 발급 없음’으로 단정해서는 안 된다.

기존 서버 설정을 확인하려고 임시 SSH 자료 취득을 요청했지만 **자동 승인 검토가 거절**했다. 명시된 이유는 ‘AWS 인스턴스의 SSH 개인키·인증서를 회수하는 작업은 민감한 관리자 자격증명 접근이며, 승인된 NH 읽기 전용 조회만으로는 이 별도 자격증명 취득과 서버 접근을 명확히 승인하지 않았습니다.’이다. SSH 자료는 취득하지 않았고 서버 설정 접근·서버 접속도 실행하지 않았다. 간접 경로로 우회하지 않았다.

다음 조회에는 **지정된 AWS 서버의 임시 SSH 인증자료 취득과 기존 앱 인증 설정의 읽기 전용 확인**에 대한 구체적인 추가 승인이 필요하다. 승인 후에도 실제 앱의 잔고 대조 경로만 사용하고 주문·장부 쓰기·서비스 변경·배포는 하지 않는다. 다른 방법으로 현재 앱의 유효한 로그인 수단이 준비되면 SSH 없이 이 경로를 사용할 수도 있다. 비밀번호를 대화에 게시할 필요는 없다.

읽기 전용 실행기 `scripts/verify_cma_existing_connection.py`는 정확히 ‘미래 성장포트’의 CMA가 하나일 때만 대조를 1회 실행하도록 준비했다. 성공하면 조회 전후 계좌 장부가 같은지도 확인한다. CMA가 여러 개면 추측하여 조회하지 않는다. 합성 시험으로 로그인 실패·복수 CMA·NH 실패 시 조회를 반복하거나 별도 인증 경로로 넘어가지 않음을 검증했다.

기존 운영 대조 응답은 현금과 CMA 상품을 합한 정규화 금액이다. 이 결과만으로 `dca`·상품 평가액·업무 응답 봉투를 검증하거나 이자를 확정하지 않는다. 새 CMA 준비 코드의 실제 응답 프로필과 밤 20시 전환/다음날 반환 시각은 여전히 미확인이다. 이번 시도는 한국 시간 20시 이후였으므로, 성공하더라도 야간 금액을 이자로 확정할 상황이 아니었다.

최소 실행 결과: [읽기 전용 확인 증거](cma-existing-connection-evidence.json).

## 2. PostgreSQL: 독립 클러스터에서 실제 검증 완료

이전 오프라인 개발 때 PATH에서는 찾지 못했던 PostgreSQL **17.6** 실행 파일이 `backups/local_validation/pgsql/bin`에 남아 있었다. 이를 재사용하여 기존 로컬 클러스터·운영 DB·실제 장부 백업과 별개의 새 합성 클러스터와 `cma_synthetic` DB를 만들었다. 기존 로컬 DB도 읽거나 수정하지 않았다.

서버는 **127.0.0.1:55439**에만 바인딩했고 임의의 로컬 전용 비밀번호와 SCRAM 인증을 사용했다. `PORTFOLIO_LOAD_CONFIG_FILES=0`, NH/운영 연결 설정 제거, PostgreSQL 연결 목적지 검사, HTTP 호출 차단을 적용했다. 검증 실행기의 Windows 샌드박스 `initdb` 제한과 DB 생성 트랜잭션 사용 오류를 수정한 후 재실행했다. 이 수정은 검증 도구에만 해당하며 앱 CMA 구현은 수정하지 않았다.

`scripts/verify_cma_postgres.py`의 **13개 검증 항목 모두 통과**:

1. 기능 기본 비활성 시 CMA 스키마를 생성하지 않음.
2. 실제 앱 DDL을 두 번 실행해도 정상 초기화되고 데이터가 보존됨.
3. 네 테이블의 RLS 및 `anon`·`authenticated`·`service_role`의 스키마/이자표/시퀀스 접근 차단.
4. 같은 요청이 동시에 실행돼도 현금 증가와 이자 영수증은 한 번만 저장됨.
5. 다음날 동일 요청으로 잃어버린 응답을 복구하고 변경된 입력은 거절함.
6. 이미 기록된 외부 출금 −200,000원을 보존하고 이자 123원만 기간 이익에 반영함. 매매/보유/외부 입금 기록을 만들지 않음.
7. 다른 요청 번호가 동시에 같은 날 같은 계좌에 이자를 반영하려 해도 한 번만 성공함.
8. 잔고 증가 후 이자 저장 실패를 주입하면 잔고·이자표·요청 영수증이 모두 rollback됨.
9. 조회 중 장부 변경과 다른 포트폴리오 계좌 접근을 거절함.
10. 8개 실행기가 경쟁해도 슬롯 하나만 소비되고 재시작 후 동일 슬롯 재호출은 차단됨.
11. 잠금 안에서 자동 반영 상한 재검증, 두 번 안정된 반환 관찰 후 반영, 취소 후 자동 반영 해제 및 반복 취소의 동일 결과.
12. 이자 반영 뒤 다른 현금 이동이 있으면 취소가 새 잔고를 덮어쓰지 않음.
13. 예상과 다른 스키마 소유자이면 재사용을 거절함.

시험 후 해당 클러스터를 **종료**했고 생성용 비밀번호 파일도 제거했다. 검증 로그와 합성 DB 파일은 Git에서 제외된 `backups/local_validation/cma_pg_*`에 남겼으며 실제 금융 자료는 넣지 않았다. 외부 호출·운영 장부 쓰기·배포는 모두 **0회**다.

최소 결과: [PostgreSQL 검증 증거](cma-postgres-evidence.json).

## 3. 변경·보존·다음 단계

이번에 추가한 것은 두 검증 실행기, 읽기 전용 실행기의 합성 시험 5개와 결과 문서다. 기존 CMA 구현·프런트엔드·기간 성과 그래프·자동매수 개발 소스는 보존했다. 관련 백엔드 시험 **64 passed**이며 기존 Starlette 경고와 샌드박스 pytest 캐시 쓰기 경고가 있었다. 제품 코드/프런트엔드 변경이 없으므로 앞서 통과한 전체 백엔드 1235/프런트엔드 193 및 빌드를 반복 실행하지 않았다.

이번 작업 시작 시 기존 **457개** 파일의 해시를 저장해 대조했다. 후속 결과를 연결한 위 두 맥락/개발 문서만 변경했고 나머지 **455개**는 모두 동일하다. 기존 미커밋 변경도 그대로 보존했다. [보존 대조 결과](cma-approval-preservation-evidence.json), `git diff --check` 통과. 로컬 클러스터 종료 뒤 55439 포트가 닫힌 것도 확인했다.

남은 첫 단계는 유효한 기존 앱 인증으로 CMA 읽기 전용 대조를 받는 것이다. 조회 결과가 있어도 이자 장부 쓰기, 운영 스키마 적용·기능 활성화·배포에는 별도 승인이 필요하다. 현금/상품을 구분하는 실제 응답과 반환 시간은 검증될 때까지 추정하지 않는다. 기간 성과 그래프의 현금 제외 변경은 계속 보류한다.
