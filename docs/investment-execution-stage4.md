# 투자 실행 4단계: 최종 검증 및 배포 준비

2026년 10월 10일 · codex/investment-execution

개발·로컬 통합 검증·배포 준비를 완료했다. 운영 DB·API·실제 자산·비밀 설정에는 접근하지 않았으며 main 병합, push, 배포는 하지 않았다. 실제 운영 반영과 운영 환경 확인은 사용자 승인 뒤의 별도 단계다.

## 최종 보완

- 준비 확인 토큰에 실제 예수금·원본 계획·기존 연결 상태를 포함한다. 시작 전에 잔고가 변하면 작업 안내가 동일해도 재확인을 요구한다.
- 제외한 작업에는 새 금융 기록을 연결하지 못하도록 서버에서도 차단한다. 잘못된 연결이면 거래·잔고·원가·요청 이력까지 같은 트랜잭션에서 미반영된다. 정상 5번 독립 입력은 유지한다.
- 실제 장부에 근거해 미실행·확인 대기 작업을 계산한다. 이런 작업이 남은 경우 이유 없이 종료할 수 없다. 종료 보고서에 남은 작업과 제외 작업 ID를 보존한다.
- 투자 진행을 다시 읽는 동안 오래된 화면에서 새 작업을 입력하거나 목표를 변경하지 못하게 한다.
- 포트폴리오를 변경하면 해당 포트폴리오의 계좌 현황을 받기 전에는 투자 폼을 열지 않는다. 이전 계좌가 새 투자 시작 후보에 섞이지 않는다.
- 투자 실행 미지원 서버에서는 기존 5번 독립 기록 저장 뒤 새 투자 API 갱신을 호출하지 않아 불필요한 오류 안내를 방지한다.
- 기존 기록 연결 후보를 다시 읽을 때 이전 선택을 비운다.
- 합성 브라우저 통합 검증과 업그레이드·백업 복구 검증을 저장소에 재현 가능한 도구로 남겼다.

장부 계산식, 실제 주문·이체·환전 자동 실행, 증권사 인증정보, 클라우드 서버 구성은 이번 단계에서 추가하지 않았다.

브라우저에서는 다음 장애를 실제로 재현했다.

1. 구버전 기능 응답: 연결된 장부 요청을 보내지 않고 원래 요청을 보존한다.
2. 저장 완료 직후 응답 유실: 서버는 거래를 저장했으나 브라우저에는 연결 끊김을 전달한다. 새로고침 후 같은 요청으로 확인해도 거래·예수금·원가·연결이 한 번만 반영된다.
3. 포트폴리오 전환의 계좌 조회 지연: 새 현황을 받기 전에는 기존 계좌를 사용하는 폼을 표시하지 않는다.

모바일 320/390/430px, 데스크톱 1280px에서 가로 넘침 없음과 터치 이벤트 입력을 확인했다. 1번 최초 조회에는 투자 실행 API 요청이 추가되지 않았다. VT·PDBC 동시 매수는 같은 계좌의 기존 달러를 먼저 사용하고 필요한 환전 한 건으로 합산되는 것을 단위 검증했다.

헤드리스 도구에서 로컬 교차 출처 요청이 간헐적으로 실패하여 최종 브라우저 통합 검증은 합성 전용 Vite 프록시를 사용했다. 앱의 운영 CORS 설정은 변경하지 않았다. 허용된/허용되지 않은 Origin과 인증 헤더는 실제 FastAPI 미들웨어 테스트에서 별도로 검증했다. 외부 글꼴 요청 실패는 외부 네트워크 차단에 따른 결과다. 실제 휴대폰·실제 증권사 응답·운영 CORS/TLS/DB 권한은 별도 운영 확인 사항이다.

## 재현 방법

전용 PostgreSQL 17 합성 클러스터 127.0.0.1:55438, ledger_qa만 사용한다. 운영 접속 파일을 읽지 않는다. 다음 도구는 운영 배포 명령이 아니다.

- python -B scripts/verify_investment_execution.py
- python -B scripts/verify_investment_release.py
- python scripts/local_ui_preview.py --trust-local-port 55438 --investment-execution --port 8571
- 다른 터미널: node scripts/local_investment_ui.mjs
- 마지막: node scripts/verify_investment_execution_ui.mjs

브라우저 검증은 새 합성 UI DB로 시작해야 한다. 전용 서버 5197/8571에서 진행하여 사용자 검토용 5196/8567의 예시 기록을 변경하지 않는다. Chrome과 Node 24가 필요하다. 브라우저 프로필·화면·결과는 frontend/node_modules/.cache/investment-execution-final에 남긴다. 업그레이드/복구는 실행마다 새 DB를 만들고 끝나면 삭제하며, 합성 백업·결과만 ignored backups/local_validation/investment_release에 보존한다.

## 남은 승인과 운영 확인

개발 결과를 검토한 뒤 main 병합·origin push 승인만 받으면 배포 절차를 진행할 수 있다. 그때 최신 운영 백업과 메타데이터 점검을 수행해야 하며 과거 백업이나 이번 합성 복구 성공을 실제 운영 백업으로 대체하지 않는다.

실제 적용 순서, 권한의 성공 조건, 장애 시 대응은 [investment-execution-deploy-ko.md](investment-execution-deploy-ko.md)에 정리했다. 사용자 검토용 합성 앱은 http://127.0.0.1:5196/ 이다.
